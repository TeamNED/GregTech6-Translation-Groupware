# 算法性能评估（2026-10-23）

> **monorepo 路径说明：** 原 `src/`、`workplace/` 已移动到 `packages/legacy/`；本文历史段落中的 `workplace/...` 均指 `packages/legacy/workplace/...`。


目标：在**同一语言实现**（Node.js 24.21.0）下，对比六种算法，验证“新算法必须比现有正向物化方案更快”这一 blocker。前三种（forward / stream / token）是最初的基线；第 7–9 节追加 strict-token、grammar、flat-token 和编译型 pattern 引擎。

- A `forward`：忠实复刻现有 C++ 算法——先展开所有 completed 生成器的笛卡尔积，存入 `Map<原文, 条目[]>`，最后逐 key 查表。
- B `stream`：仍正向展开，但每生成一个 pair 立即用输入值集合过滤，只保留可能命中的条目。
- C `token`：把 completed-only 规则的模板编译为「字面量 + 占位符」匹配器，直接拿输入值切分，捕获后到子组哈希表查译文；不展开笛卡尔积、不使用正则。

三个实现共用同一份配置模型、语言文件解析、group 求值语义和输出逻辑，因此差异只来自算法本身。

## 1. 测试环境与语料

- Node.js v24.21.0，Windows 10 x64，每次运行独立进程，`--max-old-space-size=8192 --expose-gc`。
- 每组 5 次，取中位数；同时记录最小值、峰值 RSS（`process.resourceUsage().maxRSS`）和结束时的堆占用。
- 三个引擎的输出必须逐条一致：对比完整 key→value 映射的 SHA-256；同时校验 unknown 集合。
- 语料：
  - `real`：真实配置，125,676 个 key，459,046 个生成 pair。
  - `scale4`：把整份配置/语言文件/fallback/golden 复制成 4 个 addon 命名空间（`S:a1.`…`S:a3.`），502,704 个 key，约 184 万生成 pair。
  - `explode`：在真实配置上追加 2,000 × 2,000 的两组词表与 4 条 `{0} {1} BigN` 规则，共 400 万生成 pair，但输入中只有 100 条能命中。

## 3. 解读

1. **现有正向算法的内存随生成 pair 数线性增长。** `explode` 场景 443 万条目 → 1.92 GB 堆、2.21 GB RSS，正好复现了用户观察到的 ~2 GB；`scale4` 的 174 万条目 → 552 MB 堆。
2. **流式过滤把内存与生成量解耦。** 即使 400 万 pair，堆仍只有 182 MB，因为不命中的 pair 立即丢弃；代价是仍然要枚举 400 万次组合（1.55 s）。
3. **分词器避免了枚举，但有每 key 的解析/规则求值开销。** 在真实语料上它比流式慢约 27%（0.80 s vs 0.63 s）；在 4× addon 上也慢约 13%。但当“生成量 / 命中量”很高（explode 为 400 万 / 100）时，它是唯一不随生成量增长到不可接受的方案：0.71 s，比流式快 2.2×，比现有正向算法快 5.7×。
4. **纯 JS 已经足够快。** 参考此前 Release C++ 全量 1.0 s / 215 MB（单次），JS 流式 0.63 s / 190 MB 堆；纯 JS 不劣于现有 C++，因此 N-API 加速不是当前的必要项，应作为后续基准项而不是前置项。
5. **一个必须记住的语义坑：** fallback 文件里存在重复 key（例如 `S:"fluid.molten hsla"` 连续两行，第二行 value 以 `=` 开头）。C++ 用 `std::map::insert`，**首次写入获胜**；JS 的 `Map.set` 是后写覆盖。原型在修正为“首次获胜”后才做到逐字节一致。
6. **另一个实现坑：** 不要用单个 float 编码 `(generator, rule, combo)` 排序。4× 配置下生成器数量达到数千，`generator * 1e12` 超过 `Number.MAX_SAFE_INTEGER`，导致条目被误判为重复。原型改为三元组比较后，scale4 才恢复一致。

## 4. 决策（2026-10-23 初版）

> 2026-10-24 更新：编译型 `pattern` 引擎已在真实、4× addon、400 万对三套语料上完成逐条 parity，默认引擎改为 `pattern`；`stream` 保留为多 addon 绝对速度回退。详见第 9 节。

**初版默认引擎：`stream`（2026-10-24 已被 `pattern` 取代，见第 9 节）。**

- 真实配置：比现有正向算法快 1.16×，堆内存少 31%（277 → 190 MB）。
- 4× addon：快 1.21×，RSS 低 23%（953 → 736 MB）。
- 组合爆炸：不爆内存（182 MB vs 1.92 GB），代价是仍要枚举。
- 实现简单，与现有语义最容易对齐，是迁移第一阶段的最佳落点。

**可选引擎：`token`，按配置自动选择。**

- 触发条件：估算 completed-only 规则的生成量 `P` 与输入 key 数 `K` 的比值。实测在 `P/K ≈ 3.6–3.7` 时流式更快；在 `P/K ≈ 32` 时分词器明显胜出。
- 建议初始阈值 `P > 8 × K` 时启用 tokenizer；上线后用真实配置回归校准。
- 分词器不需要正则；模板只由字面量和 `{n}` 组成，用 `startsWith`/`indexOf` + 哈希查表即可。
- 分词器目前不支持相邻占位符（`{0}{1}`）的通用切分；当前配置没有这种模板。应加 lint：出现相邻占位符时回退流式引擎，或用有界切分。
- 两个引擎必须长期共用 parity 测试；任何输出差异都视为 bug。

**N-API：暂不作为默认路径。** 纯 JS 已经优于现有 C++ Release 基线；只有在后续 profiling 发现真实热点、且 N-API 在真实和 10× 配置上都 ≥2× 时才引入。

## 6. 局限

- 单机单次会话的中位数，未固定 CPU 频率；绝对值会波动，但相对排序在 5 轮中稳定。
- `explode` 与 `scale4` 是合成语料，用于验证伸缩性，不代表真实 addon 的键空间分布。
- `maxRSS` 包含 Node 运行时基线（约 75 MB）。
- 分词器的解析缓存和候选去重会增加内存；当前版本以“正确 + 不爆炸”为优先，尚未做极限调优。
- C++ 基线来自此前 Release 构建的单次测量（1.0 s / 215 MB），仅作参考，不与 JS 数字做严格等价比较。

## 7. 追加实验：严格分词、token 级语法与扁平匹配

在「不要被现有实现束缚」的前提下，又实现了两个不依赖字符级 `indexOf` 的版本：

- `grammar`：把 `config.yml` 编译成 token 级上下文无关语法（CFG）。字典条目是终结符产生式，规则模板是「终结符 + 非终结符」产生式；输入先严格分词，再用带记忆化的自顶向下解析器解析整个 token 序列。
- `flat-token`：只保留一层规则。被引用的组仍然正向建表，但表键是 **token 序列** 而不是原文字符串；completed-only 规则直接按 token 边界切分并查表，不做递归语法解析。

### 7.1 严格分词暴露的真实问题

现有配置里有 **3 条词内拼接规则**，它们在空格/标点分词下无法切分：

| 组 | 模板 | 说明 |
| --- | --- | --- |
| `toolHead` | `{0}Crush Hammer Head` | 生成 `AbyssalniteCrush Hammer Head`，材料名与后续词粘成一个 token |
| `mold` | `Extruder Shape for making {0}s` | `Plate` + `s` 变成 `Plates`，后缀在 token 内部 |
| `mold` | 同上（subs = `shapeAlias`） | 同上 |

处理方式：在语法编译阶段检测「占位符与字面量之间没有空格/标点」的规则，把该组的每个条目**特化成具体产生式**（例如 `AbyssalniteCrush Hammer Head`、`Plates` 各自成为一条 token 序列）。这样运行时仍然是纯 token 匹配，不需要字符级回溯。不特化时 622 条译文对不上；特化后与 golden 完全一致。

如果未来要彻底采用严格分词，这 3 条规则应作为配置迁移项，或在 schema 中显式标记 `affix` / `suffix`，而不是依赖隐式拼接。

### 7.3 结论

1. **严格分词是可行的、可以做到逐条一致**，但在这份配置上不带来速度优势。原因是当前语料以「多词组合 + 少量后缀拼接」为主，正向枚举 459k 个 pair 在 JS 里本来就很便宜；严格分词反而要为 102k 个被引用条目建立 token 表、为每个输入值建立 token 跨度。
2. **CFG 语法解析器太慢**（真实 1.57 s，是优化后流式的 4.4×）。它的优势是活堆极低（GC 后 28 MB）和表示能力，不适合作为默认执行引擎。
3. **flat-token 是最有潜力的严格分词变体**：真实 0.843 s、活堆 69 MB，比 grammar 快一倍，且完全保留 token 边界语义。它目前比优化后的流式慢约 2.4×，主要成本在 group token 表构建和 span key 分配；如果改成 group token trie + 懒加载，有希望接近甚至超过流式。
4. **（2026-10-24 更新：见第 9 节）** 编译型 `pattern` 已经实现并超过本节结论：真实 0.611 s / 63 MB、爆炸 0.595 s / 65 MB、4× 2.445 s / 154 MB，默认引擎改为 `pattern`；`stream` 保留为多 addon 绝对速度回退。
5. 严格分词的方向由 `pattern` 继承并落地（编译期展开模板 + 运行时 `LIT`/`LEX`/`REDUCE`），`grammar` / `flat-token` 保留为研究基线和对照。

## 8. 流式引擎的二次优化与增量缓存（2026-10-24）

### 8.1 已落地的优化

1. **原文优先**：completed-only 规则先只构建 `src`，命中 `inputValues` 后再合并 namespace、构建译文。真实配置 72.9% 的 pair 不命中，这部分译文/namespace 工作被直接省掉。
2. **单候选快路径**：apply 阶段 `arr.length === 1` 时直接判断 namespace，不做 `betterOrder`。apply 从 ~0.19 s 降到 ~0.07 s。
3. **首词前缀剪枝**：实测收益不稳定（completed-only 0.214 → 0.199 s，但总时间略增），默认关闭，保留为开关。

优化前后（同一语料、同语言）：

| 场景 | 优化前 stream | 优化后 stream | 提升 |
| --- | ---: | ---: | ---: |
| 真实 | 0.483 s | **0.354 s** | 27% |
| 4× addon | 2.389 s | **1.144 s** | 52% |
| 400 万 pairs | 1.523 s | **0.965 s** | 37% |

### 8.2 阶段拆分（真实配置）

| 阶段 | 时间 |
| --- | ---: |
| 被引用组构建 | ~0.08 s |
| completed-only 枚举 | ~0.21 s |
| apply | ~0.07 s |
| apply（候选已在内存，热路径） | **~0.039 s** |

结论：**剩余成本主要是「生成 361k 个 completed-only pair」**。继续微调匹配算法只能带来常数级收益；要跨数量级，必须避免重复生成。

### 8.3 增量缓存（下一步最大的实际收益）

对每个 group 做内容寻址缓存：

```
hash(group) = hash(生成器定义 + 所有子组的 hash)
```

- 第一次运行正常生成，把每个组的结果写入 `.cache/groups/<hash>`（二进制或压缩 JSON）。
- 后续运行只重新生成 hash 变化的组；其余直接加载。
- 最终 apply 始终执行（它只依赖输入 key 和候选表）。
- 翻译工作流中大多数修改只影响 fallback 或少量规则，缓存命中率会很高。

按 8.2 的阶段拆分：

- **长驻进程/Web 服务**（解析结果和候选表都在内存）：small edit 后重算约 **0.04–0.1 s**（只剩 apply）。
- **冷启动 + 磁盘缓存**：仍需解析 125k 条语言文件并加载缓存，进程内完整耗时约 **0.25–0.3 s**；相对冷启动全量生成（进程内 0.65 s）仍快一倍以上。

缓存放在磁盘并按 hash 淘汰，可以避免现有实现「2 GB 内存缓存」的问题。

### 8.4 并行枚举

completed-only 的 generator 互不依赖，可以用 `worker_threads` 按 generator 分片。4 核理论上可把 0.21 s 的枚举压到 ~0.06 s；主要成本是候选表合并。适合 CI/批量构建，不建议作为默认交互路径。

### 8.5 最终建议（2026-10-24 更新）

本节写于 `pattern` 引擎完成之前。结合第 9 节：

- **默认**：`pattern`（0.611 s 真实 / 2.445 s 4× / 0.595 s 爆炸；活堆 63/154/65 MB）。
- **多 addon 绝对速度**：`stream`（4× 2.243 s，比 pattern 快 9%，但活堆 552 MB）。
- **极端 P/K**：`token` 作为备选；`pattern` 在 400 万对场景已只需 0.595 s。
- **`stream` 回退路径的重复小改动**：增量缓存仍有价值（预计 ~0.1 s）。
- **不要用 grammar 作为默认引擎**；严格分词已由 `pattern` 采用。



## 9. 编译型扁平模板引擎（2026-10-24）

### 9.1 背景：对「空格分词 + 双 Trie + 拆并重试」的验证

用户提出四点新思路：

1. 分词只看空格；
2. 分为词汇词和非词汇词两棵 Trie；
3. 模板只处理非词汇部分，所有中间模板保留，最后编译为一个 Candidate，每个 Slot 标注是否接受词汇词；
4. 出错时查看前后 token，尝试拆分当前 token 或合并相邻 token 后重试。

原型 `pattern-bench.js` 把这四点中真正影响性能的部分实现为**编译型扁平模板自动机**，并与 golden 逐条对比。

### 9.2 数据核验

| 指标 | 数值 | 结论 |
| --- | ---: | --- |
| 规则模板 / 槽位 / 字面量 token | 162 / 202 / 116 | 规则图很小 |
| 槽位组类型 | 121 dict-only / 23 rule-only / 57 mixed / 1 missing | 双 Trie 无法严格二分类 |
| 混合组解析调用 | 721,473 | 占 grammar 解析调用 56.8% |
| 混合组按首 token 可分流 | 70,894 dict-only + 557,274 rule-only vs 90,384 both | 87% 可只走一侧 |
| 空格分词不一致 | 16,042 | `-` 14,107、括号 2,100、`/` 124、`&` 80、`,` 75、`.` 10 |
| 标点拆分重试成本 | 0.129 s（tok 0.032 + gather 0.027 + parse 0.070） | 不值得作为主路径 |
| 需要合并相邻 token 的案例 | 0 | 合并不是当前需求 |
| affix 规则 / 特化条目 | 3 条 / 1,632 条 | 编译期特化即可，无需运行时任意拆分 |
| 展开后的结构模板 | 972（全部组）/ 899（completed 顶层）/ 993（去重 pattern） | 规模可控，无爆炸 |
| 最大单组展开模板 | 75–77 | 没有组合爆炸 |

这里的 202 是 162 条规则模板中 `{n}` 占位符的出现次数，不是 143 个唯一 group；每个槽位由 `subs[n]` 指定目标 group。按唯一 group 分类是 54 dict-only / 79 rule-only / 10 mixed；57 个 mixed 槽位引用只对应 10 个唯一 mixed group（`material` 一个组就被引用 34 次）。

### 9.3 编译与执行

1. **严格分词 + ASCII 快路径**：单词/标点/撇号；空白不作为 token。避免「空格分词 + 重试」的双路径成本。
2. **词法表**：dict 条目和 affix 特化条目按首 token 建 `Map<token, entries[]>`。
3. **模板展开**：对每个组递归展开规则树；dict 组保留为 `LEX` 槽，规则组继续展开，混合组同时保留两者。每条路径编译为 `LIT` / `LEX` / `REDUCE` 操作序列。
4. **元数据**：每组的 `minLen/maxLen/firstSet/lastSet`，每条规则的 `slotOrder/subSizes/base/tgtParts`。
5. **索引**：首 token 索引 + namespace trie（与 grammar 相同的前缀继承）+ 末 token/必需字面量剪枝。
6. **执行**：`LIT` 比较 token；`LEX` 枚举匹配词条；`REDUCE` 合并 namespace、计算 combo、构建译文。回溯时用 `minSp` 保存/恢复外层 `LEX` 循环的父操作数。多词词条（如 `Infused Earth Crystal`）是 `terms` 为 3 个 token 的单个 `LEX` 条目，一次消费 3 个 token；不是合并回退，栈只合并槽位结果。

### 9.4 结果（3 轮中位数，端到端，`--expose-gc`）

### 9.5 四点逐条结论

| 提议 | 结论 |
| --- | --- |
| 1. 只看空格分词 | **不推荐作为唯一分词。** 16,042 条不一致；对失败值做标点拆分重试约 0.13 s，且需要双分词器/双优先级路径。直接用标点感知的 ASCII 快路径分词，成本更低且 0 差异。空格分词可以作为「先粗后细」的优化，但当前数据没有收益。 |
| 2. 词汇词/非词汇词两棵 Trie | **部分可行。** 57/202 槽位引用混合组，无法严格二分类。但 87% 的混合组解析调用可仅凭首 token 分到一侧；实现上用「`LEX` 词法表 + 编译后的规则分支」达到同样效果，不需要强行把每个槽位标成单一类型。 |
| 3. 中间模板保留并编译成 Candidate | **完全可行，且是性能关键。** 展开后只有 972 条结构模板；运行时不再递归 `parseGroup`，真实/爆炸配置达到或超过 stream，活堆只有 1/3–1/5。 |
| 4. 拆分/合并相邻 token 重试 | **拆分是空格分词的必需品，合并不是。** 当前语料 0 条需要合并；拆分需求全部来自标点边界和 3 条 affix 规则。affix 在编译期特化成 1,632 条具体词条后，运行时无需任意位置拆分。建议保留为未来 addon 的安全网，而不是主路径。 |

### 9.6 决策与取舍

- **默认引擎改为 `pattern`。**
  - 真实：0.611 s / 63 MB，与 `stream` 基本持平，活堆少 3.0×。
  - 爆炸：0.595 s / 65 MB，比 `stream` 快 2.15×，与 `token` 基本持平，活堆少 4.8×。
  - 4× addon：2.445 s / 154 MB，比 `stream` 慢 9%，但活堆少 3.6×。
- **`stream` 保留为速度回退**：多 addon 且输入 key 很大、或 `pattern` 编译出的模式数异常膨胀时使用；它仍是最简单、最稳妥的 parity 基线。
- **`token` 保留为极端 P/K 备选**：当规则图很小但组合数极大，且 `pattern` 因规则图/候选异常不适合时。
- **`grammar` 保留为研究原型**：活堆极低，但 1.12–1.57 s，远慢于 `pattern`。

### 9.7 局限与后续

- 峰值 RSS 仍约 376 MB（启动/编译垃圾）；活堆 63 MB。若峰值 RSS 是硬指标，需要调 GC 或流式编译。
- 3 条 affix 规则目前靠编译期特化；schema v2 应显式标记 `affix`/`suffix`，避免新增规则漏检。
- 过滤器收益高度依赖 pattern 宽度：真实配置下全局 `max` 在宽度 0 的 pattern 上拒绝 78.5%，宽度 1–2 拒绝 18.5%，宽度 3–5 仅 1.5%，宽度 ≥6 低于 0.1%。宽 LEX 场景不要指望 `max`；全局 `min` 仍有约 12% 的硬下界收益。LEX 后缀约束中 `remMax` 有效（lexHits −5%），`remMin` 几乎无效；宽 LEX 的主要优化是词法 token trie（lexAttempts −30%）。
- 栈回溯的 `minSp` 保存/恢复是正确性关键；改成树式递归执行器可以去掉这部分开销（估计 0.05–0.15 s）。
- 当前原型使用严格分词；空格分词 + 局部拆分重试在算法上可行，但在本语料上没有速度收益。
- 书本/散文仍不覆盖；`pattern` 只解决模板词条，不解决长文本。
